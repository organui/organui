# OrganUI registry foundation

OrganUI distributes editable source through a shadcn-compatible registry. The first item is an anatomy tree; it accepts application data and callbacks without any viewer, organ model, sibling checkout, or unpublished runtime dependency.

## Boundaries

- `packages/ui` remains the private website foundation (Base UI / Nova, theme and internal components).
- `packages/registry/registry/base-nova/anatomy-tree/anatomy-tree.tsx` is the public installable source, laid out as `registry/[STYLE]/[NAME]` per the [shadcn registry guidelines](https://ui.shadcn.com/docs/registry/getting-started). New items follow the same layout. It imports React, `cn` (the class-merging package shadcn's own components import, so a consumer's `className` overrides the defaults) and shadcn's `button`, `input`, `field` and `empty` from `@/components/ui/`, which the shadcn CLI rewrites to the consumer's UI alias. The organ viewer does the same with `alert`, `button`, `progress`, `select` and `tooltip`; its three.js canvas is plain DOM. Inside this repository that alias resolves, through `paths` in `packages/registry/tsconfig.json` and `apps/web/tsconfig.json`, to the base-nova copies in `packages/ui/src/components`, which the website installs with the shadcn CLI and never edits by hand. The private workspace export lets the website demonstrate that same source without duplicating it. Consumers never import the workspace package.
- Item types follow one rule: clinical widgets composed from shadcn primitives (`anatomy-tree`, `body-map`, `vital-signs`, `lab-results`, `ecg-trace`, `medication-schedule`, `dermatome-map`, `image-viewer`, `growth-chart`) are `registry:ui` and install beside shadcn's components in `components/ui`; three.js scenes (`organ-viewer`, every organ, `molecule-viewer`, `dna-helix`) are `registry:component` and install in `components`. `packages/registry/tests/blocks.test.ts` checks it.
- Each of the 42 organs follows `registry/base-nova/<name>/<name>.tsx`, just like other component items. For example, `heart/heart.tsx` exports `Heart`, `HeartProps` and `heartModel`; the private workspace export is `@workspace/registry/heart`. The shared renderer stays in `organ-viewer/organ-viewer.tsx`. Organ components import it through `@/components/organ-viewer`, which the CLI rewrites to the consumer's component alias. Every organ is its own `registry:component` item that ships only its public wrapper and declares `registryDependencies: ["@organui/organ-viewer"]`, the way shadcn's chart items ship one file and depend on `chart`. The viewer item carries three.js and the official shadcn dependencies, so it installs once and every organ shares it. No two items ship the same file, and blocks likewise ship only their page and layout files and depend on the `@organui` items they import (`packages/registry/tests/blocks.test.ts` enforces both). Because the dependency is namespaced, consumers register `@organui` in `components.json`; GitHub installs resolve it from organui.com too, as shadcn does not pass a `#ref` on to dependencies. Adding another organ preserves an existing renderer unless the consumer explicitly overwrites it. Generator scripts use the same per-organ paths. Tests cover every wrapper's bound model, callbacks, ref, source and controls, as well as model metadata and licences.
- `packages/registry/registry/base-nova/lab-results/lab-results.tsx` is the `lab-results` item, a stateless table that imports shadcn's `table` and flags values against reference ranges passed as data. It has no client directive, so it also renders in server components; the Next.js consumer serves it from a server page at `/lab`, which `tests/browser/lab.spec.ts` drives.
- `packages/registry/registry/base-nova/growth-chart/growth-chart.tsx` is the `growth-chart` item: LMS percentile curves, z-scores and plotted measurements over reference tables the application passes. It ships no data and no loader, because WHO's growth standards need WHO's permission for commercial reuse; `growthStandardsFromAnthro` only parses tables in WHO's anthro layout that the user brings. The docs demo fetches WHO's tables at runtime through `apps/web/lib/who-growth-standards.ts`, which is not part of the item. Tests and the consumer harness at `/growth` use made-up tables, and the docs browser test routes WHO's URLs to them.
- Explorer models are not copied into this repository. Each such organ's `src` is a jsDelivr URL pinned to a full explorer commit, so the mesh is served from the repository that documents its provenance and licence (BodyParts3D CC BY-SA 2.1 JP or CC BY 4.0, Z-Anatomy CC BY-SA 4.0, HuBMAP CC BY 4.0, the CC0 skin model). The viewer displays the credit and licence link by default. Tests never fetch them: the browser suite serves a generated box model from `packages/registry-e2e/scripts/fixture-glb.ts`.
- Organs without an explorer repository, starting with `nerves`, are built here: `models/<organ>/prepare.ts` (its own non-workspace package, run with `bun install && bun run <organ>` in `models/`) writes `apps/web/public/models/<organ>.glb` and a manifest, and `models/<organ>/ATTRIBUTION.md` records source, hashes and licence. The item's `src` is `https://organui.com/models/<organ>.glb`, which `apps/web/next.config.ts` serves with CORS for installed viewers; `organ-models.ts` rewrites it to the same-origin path for opt-in catalog previews and model metadata. Named component demos use the component's public default URL, just as installed consumers do. `organs.test.ts` checks the committed GLB's size and node names against the item.
- `packages/registry/registry/base-nova/molecule-viewer/` and `dna-helix/` hold the two `molecular` items. Each is one self-contained file on the same three.js stage conventions as the organ viewer (controlled selection, keyboard rotation and zoom, a WebGL failure message), plus a sequence strip that is the keyboard and screen-reader route to selection. The molecule viewer parses PDB and PDBx/mmCIF itself (first model, first alternate location, author numbering, HELIX/SHEET or `_struct_conf`/`_struct_sheet_range`) and infers bonds from covalent radii. Its sample, `apps/web/public/models/crambin.pdb`, is wwPDB CC0 data with `crambin.ATTRIBUTION.md`; `packages/registry/tests/molecules.test.ts` checks the parser against it and against PDB and mmCIF copies of 1A8O in `tests/fixtures`.
- `packages/registry/registry.json` declares catalog metadata, npm dependencies and the `registry:ui` file. The root `registry.json` only `include`s it, which makes the repository a [GitHub registry](https://ui.shadcn.com/docs/registry): `organui/organui/<name>[#ref]` installs from source without the website. The shadcn CLI chooses the destination from the consumer's `components.json` UI alias. `registryDependencies` lists bare shadcn names (`button`, `select`...), which always resolve to shadcn's own registry in the consumer's style, so URL, namespace and GitHub installs fetch them the same way and skip any the consumer already has. There are no global styles or theme overrides.
- `packages/registry/scripts/build.ts` runs `shadcn registry validate` on the root registry, clears `packages/registry/dist`, runs the pinned `shadcn build registry.json --output dist`, then validates the catalog and every generated item against the installed shadcn schema, checks that the output holds exactly the catalog and one file per item, and rejects private imports.
- `apps/web/scripts/stage-registry.ts` owns copying those artifacts into `apps/web/public/r`, resolving them through the `@workspace/registry/dist/*` export of its workspace dependency rather than a sibling path. The site serves `/r/registry.json` and `/r/anatomy-tree.json` as static assets.
- `apps/web/app/docs/layout.tsx` is the shared documentation layout: a site header, a sidebar on desktop and a menu on mobile. `apps/web/lib/registry.ts` reads `packages/registry/registry.json` (exported as `@workspace/registry/registry.json`) so the sidebar and the `/docs` index list every catalog item with its install command; each item needs a page at `apps/web/app/docs/<name>`, which the browser suite checks. Organ items share the generated `apps/web/app/docs/[name]` page, which loads models through `apps/web/lib/organ-models.ts`, and are listed under their own sidebar section by their `organ` category.
- `apps/web/app/docs/components/anatomy-tree` contains documentation referencing the named live example in `apps/web/examples/anatomy-tree-demo.tsx`. The homepage only adds a discovery link to `/docs`.
- Documentation adapts shadcn/ui's `ComponentPreview` → `ComponentPreviewTabs` + `ComponentSource` split. Pages reference named demos, such as `<ComponentPreview name="heart-demo" />`. `apps/web/examples/_registry.tsx` resolves each name to its renderer, title, and actual example source file; `_organs.tsx` explicitly maps all 168 organ demos to their own files. Each organ demo imports the public organ component, without model injection or placeholder props. The standalone viewer demos import their model explicitly, matching that component's public API; examples are separate from installable component registry items. `ComponentSource` reads that file on the server, rewrites workspace imports to consumer paths, and highlights it using a documentation-only high-contrast Shiki configuration. There are no handwritten preview-code strings. `DeferredPreview` adds viewport-based mounting for expensive 3D examples; `OrganViewer` remains only the 3D runtime. `organ-examples.tsx` lays out named sections using the same shared preview. All organ pages start with simple public-component usage and include a typed API table. The primary demo preserves runtime defaults; other sections show Without Controls, Controlled Selection, and With Anatomy Panel. Code reveal preserves live state. Compact index previews remain opt-in. Upstream adaptations are pinned to shadcn/ui commit `daaf156ee00ed91cc7e6bdd937c1b4973152d141`; the upstream MIT notice is retained in `apps/web/components/SHADCN-LICENSE.txt`.
- The site layout follows shadcn/ui's `apps/v4` at commit `a13329f173f332a5585faa4af7e1c5ea8b2034a1`: a header with Docs, Components, Organs and Blocks, ⌘K search, the GitHub star count and a theme toggle; guides at `/docs/<slug>`; components at `/docs/components/<name>`. `/docs/<name>` redirects permanently to the component page (`next.config.ts`), because items installed from v0.3.0 and earlier print that address. Sidebar groups come from registry categories (`clinical`, `imaging`, `molecular`/`cell`, `anatomy`/`organ`); the Organs group links the organs gallery (`/docs/components/organs`) instead of listing every organ, and the components index is an A–Z list of links, as on shadcn/ui. Search fetches the static `/search.json` and loads its dialog on first use, so pages carry neither.
- `/docs/components/organs` (redirected from `/organs`) shows every organ A–Z as a picture linking to its page, without the right-hand contents column (`data-docs-wide`). Each organ also carries one of the 11 body systems in `packages/registry/body-systems.json` as a registry category, which the site doesn't show yet. A picture is a rendering of its model, so it keeps that licence; the page points to Licences for every credit. `bun run thumbnails` (`apps/web/scripts/organ-thumbnails.ts`, after shadcn/ui's `capture-registry.mts`) renders organs without a picture, or those named with `--only`, through `/thumbnail/<name>`, a page that exists only under `next dev` with `ORGANUI_THUMBNAILS=1`. `apps/web/lib/organ-thumbnails.json` records the model each picture was rendered from, and `apps/web/tests/organ-thumbnails.test.ts` fails when a model changes without a new picture.
- `packages/registry/registry/base-nova/body-map/body-map.tsx` is the `body-map` form input: a front and back SVG outline whose regions are checkboxes, with a controlled `value` of region IDs, `onValueChange`, and an optional `name` that submits hidden inputs. It imports only shadcn's `button`. The outline was drawn for this item as a simplified diagram; paired shapes are drawn once on the viewer's left and mirrored, so from the front the person's right is on the left. `packages/registry/tests/body-map.test.ts` checks IDs, sides and that arrow keys reach every region, and `tests/browser/body-map.spec.ts` drives the installed copy in both consumers.
- `packages/registry/registry/base-nova/ecg-trace/ecg-trace.tsx` is a `registry:ui` rhythm strip drawn in SVG, in millimetres of ECG paper so the grid stays square at any width. It takes recorded samples or a `subscribe`-style stream (a monitor sweep with a pause button, shadcn's `button`), and ships its own heuristic wave detector and synthetic rhythm so it needs no data to demo. The detector is a labelling aid for clean rhythms, documented as not for diagnostic use; `packages/registry/tests/ecg-trace.test.ts` covers it and `tests/browser/ecg.spec.ts` drives the installed strip.
- `packages/registry/registry/base-nova/dermatome-map/dermatome-map.tsx` is a `registry:ui` front and back body map of the 28 ISNCSCI sensory levels, drawn as inline SVG, with a single-tab-stop level list (shadcn's `button` clears the selection). Its paths are generated by `packages/registry/scripts/dermatome-map.py` (Python and shapely), which draws one half of each figure and splices the `shapes` constant into the component; the other half is mirrored at render. It is a simplified illustration, documented as not a clinical tool; `packages/registry/tests/dermatome-map.test.ts` covers it and `tests/browser/dermatome.spec.ts` drives the installed map.
- Future versioned runtime packages should be introduced only when a shared, stable runtime contract is justified. This registry is source distribution, not an npm anatomy runtime. Explorer asset repositories remain independent.

## Component decisions

The public props are `data`, `selectedId`, `onSelectionChange`, `visibility`, `onVisibilityChange`, `defaultExpandedIds`, `label`, and `className`. Data is a readonly hierarchy of `{ id, label, children?, color?, selectable? }`; `color` is a CSS color drawn as a decorative swatch, and `selectable: false` makes a grouping row expand or collapse on click or Enter instead of selecting (it then has no `aria-selected`). IDs must be globally unique and nonempty. No anatomical asset is included. The simplified heart labels were written for this example, not extracted from a model dataset.

Tree-specific label and expand buttons use local CVA variants over the Base UI button primitive, so tree row styling does not override a consumer's shared Button variants. The search uses Field composition, and missing/filtered data uses Empty composition with a live status.

Selection is controlled and independent of focus and visibility. Only Enter or clicking a label selects. Consumers reconcile removed selections themselves. Visibility is a controlled leaf-ID map; absent entries mean visible. A branch is checked when all leaves are visible, unchecked when none are, and mixed otherwise. A branch action changes every leaf, even when descendants are filtered or collapsed. Mixed branches become fully visible. Branch entries do not override leaf entries. Callbacks remove unknown IDs; newly introduced leaves default visible.

Expansion and search are local UI state. Search uses case-insensitive label matching, includes ancestors, and temporarily expands the matching paths without mutating saved expansion. A matching branch does not include all its nonmatching descendants. Collapse is disabled while searching. Stable IDs preserve state on data changes; expansion defaults apply on mount only. When `selectedId` changes to a row that is not currently shown, typically a pick in the consumer's viewer, the tree adds that row's ancestors to saved expansion during render and scrolls the row into view once, inside its nearest scrolling container only so the page never jumps; a selection made from a visible row changes no expansion.

The tree uses a roving tab stop, explicit levels and sibling positions, separate `aria-selected` and `aria-checked`, and visible focus outlines. Up/Down, Home/End, Left/Right, Enter and Space are supported. Pointer buttons are Base UI buttons and are removed from the tab order; equivalent actions are available on the treeitem. Focus recovers to a visible ancestor or first row when an update removes the focused row, or to search when the tree becomes empty. Focus that left the tree deliberately, including to a non-focusable viewer canvas, is never taken back. Each visibility button's accessible name starts with its visible state text (for example “Visible: hide Heart”) so voice control can target it (WCAG 2.5.3). For the same reason each treeitem is named by its label followed by its state (for example “Heart, visible”). This is a custom tree keyboard implementation, not a claim that Base UI provides a tree primitive. Keyboard checks are automated in actual installed consumers; a screen-reader usability audit is still outside the verified scope.

The component intentionally targets small/medium in-memory datasets. It has no virtualization, lazy loading, multiselect, drag and drop, typeahead, or viewer. It uses recursive traversal; very deep or very large datasets need an adapted implementation.

Registry items draw icons with `<IconPlaceholder lucide="…" tabler="…" hugeicons="…" phosphor="…" remixicon="…" />`, as shadcn's own registry does. `shadcn add` replaces each one with the named icon from the installing project's `iconLibrary` and removes the placeholder import, so items depend on no particular icon package. In this repository `@/icons/icon-placeholder` resolves to `packages/ui/src/components/icon-placeholder.tsx`, which renders lucide like the site. `tests/icons.test.ts` checks every name against all five libraries.

## Build and cache ownership

`@workspace/registry#build` caches `dist/**`. `web#stage-registry` depends on that task and caches `public/r/**`. `web#build` depends on staging and dependency builds; `web#dev` stages before starting. Default Turbo inputs track package source and configuration; generated directories are ignored so output creation does not change input hashes. Dependency hashes propagate registry edits through staging to the website build. The website's own stylesheet (`apps/web/app/globals.css`) imports the shared theme and scans the registry source through its `node_modules` dependency link for demonstration styles; `packages/ui` does not reference sibling packages. Package-specific tasks live in each package's `turbo.json` (`extends: ["//"]`). `lint` and `typecheck` depend on a no-op `transit` task so they run in parallel while still invalidating when dependencies change.

Use root commands so Turbo orchestrates staging; running `next build` directly does not stage assets. Generated output is disposable and uncommitted. `bun run test:cache` removes both artifact directories, checks cache restoration byte-for-byte, probes source invalidation for all three task hashes, verifies changed staged content, then restores the original source and output in a `finally` block. Run it without a concurrent source editor/build.

## Commands

Requires Bun 1.4.2 and Node 22 (CI). Start with `bun install --frozen-lockfile`.

| Command                                                                    | Purpose                                                                                            |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `bun run dev`                                                              | Stage the registry and start the website                                                           |
| `bun run build`                                                            | Validate/build registry, stage assets, build Next.js                                               |
| `bun run lint`                                                             | Workspace ESLint checks                                                                            |
| `bun run typecheck`                                                        | Workspace TypeScript checks                                                                        |
| `bun run format:check`                                                     | Check formatting of this registry feature                                                          |
| `bun run test`                                                             | ID and visibility model tests                                                                      |
| `bun run test:cache`                                                       | Artifact restoration and dependency invalidation                                                   |
| `bun run test:consumers`                                                   | Generate disposable consumers, install through shadcn over HTTP, production-build Next.js and Vite |
| `cd packages/registry-e2e && bunx playwright install --with-deps chromium` | Install test browser and Linux dependencies                                                        |
| `bun run test:browser`                                                     | Generate consumers, build the website, then test actual installed components                       |

The build, consumer and browser suites are meant to run in CI, which uploads failing tests' reports as `browser-failures`. Locally, Playwright uses one worker, because each worker renders WebGL in software.

The consumer and browser suites live in `packages/registry-e2e`, which declares `web` and `@workspace/registry` as workspace dependencies so Turbo orders `consumers` after the registry build and `test:browser` after both the consumers and the website build. Both tasks are uncached because they exercise live dependency resolution. `test:consumers` creates ignored `packages/registry-e2e/.consumers/next` and `.consumers/vite` directories. It hosts the public artifact on a dynamically allocated loopback port and invokes the pinned shadcn 4.22.1 CLI: the Next.js consumer installs by URL and the Vite consumer by the documented `@organui/anatomy-tree` namespace. Vite deliberately uses `~/*` imports with `~/widgets`, `~/primitives` and `~/support` destinations to verify import rewriting rather than relying on default aliases. It never copies component source directly. Initial consumers do not include Base UI; the CLI installs it from the items' own `dependencies`. Items list `@base-ui/react` and `class-variance-authority` themselves because shadcn's published components leave those to `shadcn init`. They do include `lucide-react`, as `shadcn init` would for the configured icon library, because shadcn's `select` imports it. Checks reject private imports, preserve the consumer stylesheet byte-for-byte, require the RSC boundary for Next.js, and compile both consumers. shadcn intentionally removes the client directive for Vite's `rsc: false` configuration. Fixture templates contain only the harness and framework configuration, not duplicated component code. Each consumer then installs `heart` the same way, checks that adding `brain` preserves a customized renderer, then installs all 42 organs and compiles every named component and props export. The initial `heart` install must bring `organ-viewer.tsx` and three.js, and serves a generated stand-in GLB at `/heart.glb` for the `/organ` harness that `tests/browser/organ.spec.ts` drives (picking, the view menu by pointer and keyboard, tooltips, keyboard rotation, hidden structures, licence link). Offline, set `REGISTRY_URL` to a local server that also serves shadcn's `styles/base-nova/*.json` and `colors/neutral.json`.

Verified configuration: React/React DOM 19.2.4, TypeScript 5.9.3, Tailwind 4.2.2, Base UI dependency `^1.8.0`, shadcn `base-nova`, Next.js 16.3.3 App Router and Vite 7.3.1. Consumers use custom semantic theme tokens to verify preservation, not copied OrganUI global CSS. Other React versions, Tailwind 3, Radix presets and other frameworks are unverified. Fixture direct dependencies and CLI are pinned; downstream dependency resolution remains live to exercise real installation. The repository itself uses the frozen Bun lockfile.

The browser matrix uses ports 4318, 4319 and 4321 and refuses to reuse another service. It covers desktop/mobile website documentation plus desktop Next.js and mobile Vite consumers: navigation, independent selection, mixed visibility, filtered/collapsed descendants, no results, data replacement/focus recovery, no focus stealing after focus leaves for a non-focusable viewer, default visibility, custom theme preservation, runtime errors and overflow. The documentation checks also verify compiled styles, visible keyboard focus and served item/catalog JSON against the registry source. The website should also be visually inspected at desktop/mobile sizes when changing styling. Vite may warn that Base UI's `use client` directives are ignored, as expected for a client-only bundle.

`.github/workflows/registry.yml` runs these checks for pull requests and master pushes with read-only GitHub permissions, in two parallel jobs: quick checks (format, then one `turbo run lint typecheck test`) and the build, cache, consumer and browser suites. Superseded pull request runs are cancelled. Actions are pinned to commit SHAs, and Dependabot proposes weekly GitHub Actions and Bun updates. It does not publish packages or deploy production. Normal Vercel PR previews remain controlled by the existing integration.

## Follow-up release checks

`apps/web/vercel.json` pins dependency installation to Bun 1.4.2 with a frozen lockfile, following [Vercel's Bun pinning guidance](https://vercel.com/kb/guide/how-to-pin-a-specific-bun-version-for-vercel-builds). The build command launches `scripts/vercel-build.ts` with the same version. That script checks the root `packageManager` declaration and places the pinned executable first on PATH for Turbo's child package scripts. This changes build tooling only; Next.js keeps its existing server runtime.

Browser tests now run axe-core on the full documentation and both installed consumer pages in expanded, mixed-visibility and filtered states. These scans complement keyboard/focus tests; they do not establish screen-reader usability or complete WCAG conformance.

### Manual screen-reader acceptance checklist (not yet performed)

Use NVDA with Chrome/Firefox or VoiceOver with Safari and record the browser and screen-reader versions. A screen reader is not installed in the implementation environment.

1. Reach the search input and then the tree with Tab. Confirm the tree name, keyboard help, structure label and level are announced.
2. Use Up/Down, Left/Right and Home/End. Confirm focus, expansion and collapsed descendants are understandable without looking at the screen.
3. Press Enter to select a leaf, then Space to hide it. Confirm selection and visibility are announced as distinct states and that the parent is mixed.
4. Activate a mixed parent's visibility action. Confirm all its descendant leaves become visible without changing selection.
5. Search for `ventricle`. Confirm ancestor context is understandable, nonmatching rows are absent, and clearing search restores expansion. Search for an absent term and confirm the no-results message is announced.
6. Check an empty dataset and replacement of the focused node using the generated consumer harness. Confirm focus returns somewhere understandable without unexpectedly leaving the component.

Release review should record findings from this checklist before making any screen-reader compatibility claim.

### GitHub source smoke test

The consumer suite also creates `.consumers/github`, a separate TypeScript consumer that installs by GitHub address and registers the `@organui` namespace only so organs can resolve their `organ-viewer` dependency. CI sets `REGISTRY_GITHUB_REF` to the full PR head or push commit SHA and installs the anatomy tree and all 42 organs through the real shadcn GitHub-address path. Every component and props export is compiled. Local runs without that variable smoke-test the published anatomy tree and Heart on the default branch. It compiles the installed source, rejects private workspace imports, and verifies the stylesheet is preserved. This exercises the root registry include, the per-organ source layout, and the shared viewer. A pinned commit must already be pushed and readable on GitHub; unpushed changes are covered by the HTTP and namespace consumers. The HTTP and namespace consumers test the current working tree. This smoke test intentionally requires GitHub network access, just as the existing consumers require access to the official registry and npm.

The documentation browser checks cover ToggleGroup keyboard selection and dark-mode tree, sequence input, and option-group interaction on desktop and mobile.
